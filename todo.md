## 4. Features

Ordered by priority within each tier. Effort is relative to the existing code: **Easy** is under a day, **Medium** is days, **Hard** is weeks. Tier 1 is what is needed to develop Syntaxis with Syntaxis; tier 2 is the largest everyday gap against Claude Code and Jules; tier 3 is polish and scale.

### Tier 1: develop Syntaxis with Syntaxis

- [ ] **Issues and pull-request comments start sessions (Medium).** The Jules core loop. Add automation event kinds for an issue labelled, a pull-request review comment and an `@syntaxis` mention, and let a session continue on an existing pull-request branch. Webhook automations and GitHub connections already exist.
- [ ] **CI feedback loop (Medium).** After a push the agent reads check runs and failure logs through the user's connection (`ci_status` and `ci_logs` tools), then fixes and pushes again. Needed because Syntaxis's own integration tests need real Docker and gVisor, which a sandbox cannot nest: unit tests run in the sandbox, integration tests in CI.
- [ ] **Self-management setup (Easy to configure, Medium to verify).** A "Syntaxis development" environment image, and a rule that the agent may open pull requests to the repository but never trigger the host update itself. Depends on the verified update roll-back in section 3.
- [ ] **Session access requests: reduced restrictions for one session, granted by an admin (Hard).** A user working on a session can ask for more access than the default sandbox has, say why, and an admin approves, narrows or refuses it in the admin app. A grant belongs to that one session, names exactly what it allows, expires (hours, not forever) and can be revoked at once. It is what lets Syntaxis develop Syntaxis, and run VMs for testing. What an admin can grant, each switched on separately:
  - **Local network.** The sandbox may reach chosen addresses and ports (a test host, a build cache, a dev database), set as firewall rules for that sandbox only. Cloud metadata, the Docker socket and the Syntaxis server's own ports stay blocked whatever the grant says.
  - **Local disk.** A host folder is mounted into the workspace read-only or read-write. The admin picks the folder (checked: it must exist, may not be `/`, the data directory, another user's workspace, or anything holding the Docker socket or the master key; symlinks cannot lead out of it), and read-write needs a second confirmation. Mounted `nosuid,nodev,noexec`.
  - **Host tools.** Not by running anything on the host from inside the sandbox. The admin defines named tools in the admin app (a fixed command with typed, validated arguments, for example `vm-run <image> <script>`, `systemctl restart <allowed unit>`), and a small broker on the host, like the update service, runs them as a dedicated unprivileged user. The agent gets a `host_tool` call, each use is audited, can be set to need approval every time, and returns only the output. The sandbox never gets a shell on the host or the Docker socket.
  - **A test host or VM pool instead of the main host (suggested).** Better than giving the main host to a session: register a dedicated lab machine (with libvirt/QEMU or Docker) as a target. The broker reaches it with a key the server holds (never in the sandbox, like the commit-signing key), the VMs are disposable and have no route back to the main host, and a broken test costs a VM, not the server. A Kata or Firecracker runtime (see "Choice of sandbox runtime") would later allow VMs and nested Docker without any host access at all.
  - **No host access at all for self-development (suggested).** Much of "Syntaxis develops Syntaxis" needs none of the above: the repository in the sandbox, unit tests in the sandbox and integration tests in CI (see the CI feedback loop). Grant host access only for what genuinely needs real Docker, gVisor or VMs, and prefer the lab host for that.
  Rules that keep it safe: only a person can ask (the form in the app, never a tool the model can call, so text the model reads cannot request access); the request shows the admin the session, the repository, the user's reason and exactly what is asked, and the admin can grant less; grants are off by default, per session, time-limited, and not inherited by branches, parallel attempts or automations unless the admin says so; the session shows a banner listing what it has; every request, grant, use and revocation is in the audit log; the kill switch and a per-grant revoke remove access immediately; a granted session defaults to the "ask before risky actions" level; and any grant is a bigger blast radius for prompt injection, so it should be given only for trusted repositories. Needs real tests: a request flow through the admin app, mounts and firewall rules checked from inside a real sandbox, the broker refusing arguments outside what a tool allows, and expiry and revocation taking effect on a running session.
- [ ] **A stable, documented API (Medium).** The chat app's `/api` is internal and changes freely. Publish a versioned, documented subset (an OpenAPI file, tested against the real server) for sessions, messages, events, approvals and changes, with a rule for deprecations.
- [ ] **Outbound webhooks and email for session events (Medium).** A general "finished", "needs approval" and "failed" notification to a URL or an email address the user sets, signed, with retries. Automations can call IFTTT today, but nothing else, and push notifications and chat integration both build on this.

### Tier 2: everyday gaps against Claude Code

- [ ] **Remote models: Claude, Gemini, OpenAI, OpenRouter, GitHub Copilot and others (Medium to Hard).** Syntaxis only talks to local servers today (Ollama and OpenAI-compatible ones). Add hosted models as providers so a session can use a stronger model when the local one is not enough, with the admin deciding who may. Work, in order:
  - **OpenAI-compatible hosted services first (Easy).** OpenAI, OpenRouter, Groq, Together, Mistral and others already speak the API the OpenAI adapter reads; most need only a base address, an API key in the vault and the right model list. Check each one's tool calling and streaming for real before listing it.
  - **Native adapters for the rest (Medium each).** Anthropic (Claude) and Google (Gemini) have their own request and tool formats; each gets an adapter with tests against the real service. GitHub Copilot has no public chat API for third-party tools, so treat it as unsupported until it does and say so; it can be reached today only through a service that exposes an OpenAI-compatible endpoint.
  - **Keys and cost.** Keys are stored encrypted like other secrets and never shown. Token counts are turned into money with a price per model that the admin can edit, so quotas and the usage page can be in currency as well as tokens, with a monthly cap per user, group and provider, and a stop when it is reached. Respect provider rate limits and retry with back-off; one provider's outage must not block local ones.
  - **Privacy is the point of this project, so it needs guard rails.** Prompts, file contents and command output go to a third party. A remote provider is off for every user until the admin turns it on for them (by level, group or user); it is labelled "leaves this machine" wherever a model is picked; a session on a repository can be marked "local models only" and then refuses remote ones; secrets are still redacted before anything is sent; and the audit log records which provider a session used. The server makes the calls, so sandboxes still need no route to the internet or to the LLM server.
  - **Fit with the rest.** Model discovery, context window, tool support and the live probe work for hosted models too; the health checks that assume a local GPU (residency, VRAM, "never loads or swaps a model") must skip them; fair queueing becomes per-provider rate limiting; the helper-model and per-role routing items can then pair a cheap hosted model with a strong one. Tests: each adapter against the real service where a key is available (otherwise `NOT TESTED`), the guard rails (a user without access cannot use a remote model by any route), and cost caps stopping a run.
- [ ] **Syntax highlighting in the file editor (Easy to Medium).** The Files tab edits in a plain text box. A code editor component (CodeMirror) loaded only when a file is opened would add highlighting, indentation and search within the bundle budget.
- [ ] **Admin switches for repository content (Easy).** `repo_skills` and `repo_hooks` (a repository's skills, slash commands and hooks) have no field in the admin app yet.
- [ ] **Users request MCP servers for their own account (Medium).** Today an admin browses the registry and approves a server for everyone, and each user then switches on the ones they want. Let a user browse the same library (read-only: name, publisher, what it does, the package and version, what the review says it can reach) and ask for a server, with a reason, for their account only. The request appears in the admin app, where the admin sees the same review they see today (capabilities, warnings, whether the version is pinned) and approves, refuses, or approves for just that user. An approved server is added to that user's list on top of the ones approved for everyone, runs in its own gVisor sandbox with only that user's credentials, and follows the same rules: pinned version, untrusted output, state-changing tools ask first. The user sees the state of each request (waiting, approved, refused, with the admin's note), can withdraw it, and an admin can remove a per-user approval at any time (also from the admin's per-user settings view). Credentials: the request says which of the user's own connections or secrets the server needs; the admin never sees their values. Limits: a cap on open requests per user, and admin settings to turn the library off for users, or to approve only from a short list. Every request, decision and removal is audited. Tests: a user cannot enable an unapproved server by any route, another user's approval does not carry over, a version change on a server sends it back for review, and the request and approval flow through both apps.
- [ ] **Branching with uncommitted work (Easy to Medium).** A branched session on a repository starts at the old branch's last commit; changes not yet committed stay with the old session.
- [ ] **Better attachments (Medium).** Attachments are uploaded one file at a time and lost from the model's view after two messages; add upload progress, previews of pictures in the chat, a way to attach a file already in the workspace, and an OCR language setting.
- [ ] **Configurable workspace size and attachment clean-up (Easy to Medium).** The 5 GiB workspace limit is fixed. Make it an admin setting (instance default, and per user, level and group), and remove old files from `.attachments` after a number of days the admin sets.
- [ ] **Per-repository agent settings and `syntaxis init` (Medium).** Rules, skills, commands, hooks and notes now live in separate places. Add one page per repository that shows what applies, and a command or button that writes a starter `syntaxis.md`, commands and hooks into the repository.
- [ ] **Cost and usage per session (Easy to Medium).** Show tokens, model time and sandbox time for each session, and a rough per-day total, so a user can see what a task cost.
- [ ] **Undo for edits made in the Files tab (Easy).** Take a checkpoint before saving, uploading over or deleting a file from the Files tab, as the agent's turns already do, and offer to undo from the Checkpoints tab.

Likely built on the same API as the MCP server above, so decide the two together.
- [ ] **Move away from Bash scripts (Medium to Hard).** About 940 lines of shell (`scripts/install.sh`, `update.sh`, `update-agent.sh`, `apply-egress.sh`, `firewall-sync.sh`, `install-gvisor.sh`, `build-templates.sh` and others) do the install, update, roll-back and firewall work, and are hard to test and to port to macOS and Windows. Move that logic into the Go binary as subcommands (`syntaxis install`, `update`, `firewall apply`), with real-host tests, keeping a tiny bootstrap script that only fetches and runs the binary. Do the firewall and update paths first; it is also a prerequisite for the macOS and Windows item.
